记一次electron自动聚焦导致焦点判断失效的问题

Posted on 2026-07-30 In ElectronJS

最近排查到一个很有意思的 Electron 焦点问题：App 明明已经被其他普通窗口遮住，其他窗口也确实还在接收输入，但 Electron 却始终认为自己的窗口处于聚焦状态。

这个问题只会在一个比较特殊的启动时序下出现：App 启动后、页面尚未完成首次渲染时，用户迅速切换到其他窗口；稍后 Electron 在 ready-to-show 中调用 show()，尝试显示并激活 App。Windows 并没有真正把前台窗口交给 Electron，但 Electron 仍然触发了 focus 事件，BrowserWindow.isFocused() 也持续返回 true。

如果 App 还接收来自全局快捷键、原生设备或其他后台输入源的事件，这个错误状态就会导致一个很直观的问题：App 虽然不在前台，却仍然会响应本应只在聚焦时处理的输入。

问题在于，这三条路径最终都依赖同一个数据源——Electron 自己维护的焦点状态。一旦 isFocused() 返回的结果与 Windows 的实际前台窗口不一致，定时检查不仅无法纠正错误，反而会不断把错误的 true 写回状态管理。

显示窗口，并使窗口获得焦点。

如果只想显示窗口、不激活它，Electron 提供的是 showInactive()。

另外，官方 ready-to-show 示例使用的也是 once，而不是 on：

使用 on 时，开发环境的页面重新加载等情况可能再次触发处理逻辑，让窗口重复调用 show() 并尝试抢焦点。它不是这次问题的唯一原因，但会扩大问题出现的窗口。

真正奇怪的地方

show() 尝试让窗口获得焦点本身是预期行为。真正异常的是：Windows 没有将前台焦点交给 Electron，Electron 却认为激活已经成功。

复现时可以看到：

  • 其他普通 Windows 窗口仍然位于 Electron 上方；
  • 其他窗口仍然能够接收键盘或导航输入；
  • Electron 触发了 focus 事件；
  • mainWindow.isFocused() 返回 true；
  • 之后一直没有对应的 blur 事件。

这里需要区分两种状态：

  • Electron/Chromium Views 内部认为窗口是否处于 Active 状态；
  • Windows 当前真正的前台窗口是谁。

在当时使用的 Electron 13.6.9 中，BrowserWindow.isFocused() 最终依赖 Chromium Views 的 Widget::IsActive()；show() 则会尝试执行 Widget::Activate()。在这个特殊时序下，内部 Active 状态发生了变化，但 Windows 的实际前台窗口没有变化，于是两个状态产生了分歧。

因此，仅仅记录 Electron 的 focus、blur 和 isFocused() 是无法发现问题的。它们看到的是同一个错误状态。

用 Win32 API 确认真实前台窗口

为了确认到底是谁判断错了，我在日志中同时记录了两组信息：

  • Electron 的 mainWindow.isFocused()；
  • Win32 GetForegroundWindow() 返回的 HWND。

GetForegroundWindow() 会返回用户当前正在使用的前台窗口句柄，具体定义可以查看 Microsoft Learn。

补完日志后，问题变得非常清楚：

时机 BrowserWindow.isFocused() Win32 前台窗口
调用 show() 前 false 其他窗口
调用 show() 后 true 仍然是其他窗口
100ms 后 true 仍然是其他窗口
1s 后 true 仍然是其他窗口

这说明并不是状态没有同步到渲染进程，而是主进程同步的源数据本身就是错的。Windows 只有一个实际前台窗口，此时应该以系统返回的 HWND 为准。

在 Windows 上，getNativeWindowFocusStatus() 内部调用 GetForegroundWindow()，并将结果与 App 自身 HWND 比较。然后让所有焦点相关逻辑都走这个统一入口：

除此之外，我还做了几层防护：

  1. 将渲染进程中的初始焦点状态设为 false。窗口尚未真正成为 Windows 前台窗口时，不应该提前接收输入。
  2. 将 ready-to-show.on() 改为 ready-to-show.once()，避免页面重新加载时重复执行 show()。
  3. 在 show() 后延迟 100ms 再根据 Win32 结果校正一次状态。
  4. 在主进程的实际操作入口再次调用 isWindowFocused()，防止渲染进程中已经排队的异步任务绕过焦点变化。
  5. 对于只需要显示、不应该主动抢焦点的场景，改用 showInactive()。

这里最重要的是最后一道主进程校验。前端的状态门禁更适合改善交互，但它可能受到 IPC 延迟、状态同步或定时任务的影响。真正会产生副作用的操作，最好在执行前再检查一次系统真实焦点。

总结

这个问题最容易误判成“主进程与渲染进程状态没有同步”。因为表面上看，渲染进程保存了一个错误的 true。但把时间线补完整后会发现，状态同步其实完全正常，只是 Electron 在特殊启动时序下提供了错误的焦点状态。

这次排查最大的收获有三个：

  • BrowserWindow.show() 会显示并尝试聚焦窗口，不是单纯改变可见性；
  • focus 事件与 isFocused() 一致，不代表它们一定与操作系统的真实前台窗口一致；
  • 当功能依赖“App 必须真正在前台”这一安全边界时，Windows 上应使用 GetForegroundWindow() 与 App HWND 进行最终确认。

跨平台框架提供的抽象通常已经足够好用，但窗口焦点、置顶、全屏和输入这类与操作系统结合很深的功能，一旦遇到极端时序，最终还是要回到原生系统状态来确认。
